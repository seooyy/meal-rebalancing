# 04. 손익 시뮬레이터 (대표 메뉴 3개 × 대안 3개)

> **담당 B · 1~2일차 종일 (독립 트랙)** ([08번 역할분담](08_2일_역할분담.md))
> **카드 데이터에 의존하지 않는다.** 판매가격·변동비·판매량만 있으면 계산되므로 A를 기다릴 필요 없이 1일차 0시부터 착수한다. 셋 중 대기 시간이 가장 적다.

원문 우선순위 4번. 서비스의 핵심 기능이다. 화면 2 "우리 가게 실험안"에 해당한다.

## 목표

대안별로 **기존 공헌이익을 유지하는 데 필요한 판매량**을 계산해 비교한다. 매장 자료가 없어도 예시 조건으로 동작해야 한다.

## 계산 정의

```
건당 공헌이익 = 판매가격 − 건당 변동비
필요 판매량 = 올림[ (기존 공헌이익 + 평가기간의 추가 도입비용) ÷ 변경 후 건당 공헌이익 ]
필요 증가율 = (필요 판매량 ÷ 기존 판매량 − 1) × 100
```

- **변동비 구성**: 식재료비 + 포장비 + 결제·배달 수수료 + 판매량에 따라 달라지는 추가 노동비. 임차료·기본 인건비는 제외한다.
- **변경 후 건당 공헌이익 ≤ 0**이면 계산을 중단하고 "판매량 증가만으로는 목표 달성 불가"를 표시한다. 큰 숫자를 출력하지 않는다.
- 추가 도입비용은 평가기간(기본 4주) 전체에 배분한 금액을 분자에 더한다. 평가기간 길이를 사용자가 바꾸면 재계산한다.
- 반올림은 **올림**이다. 판매량은 정수다.

### 검산 예시 (`project_idea.md` 7절)

기존 공헌이익 600,000원 기준:

| 대안 | 판매가격 | 건당 변동비 | 건당 공헌이익 | 필요 판매량 | 필요 증가율 |
| --- | --- | --- | --- | --- | --- |
| 기존 구성 | 10,000 | 4,000 | 6,000 | 100 | — |
| 10% 할인 | 9,000 | 4,000 | 5,000 | 120 | +20% |
| 구성 조정 | 9,000 | 3,300 | 5,700 | 106 | +6% |

`600000 ÷ 5700 = 105.26 → 올림 106`. 이 세 행을 단위 테스트로 고정한다.

## 대안 4유형

`project_idea.md` 6절. 후보 카탈로그를 `config/options.yaml`로 관리한다.

| 구분 | 내용 | 조정되는 파라미터 |
| --- | --- | --- |
| 구성 재설계 | 기본 구성과 선택권 조정 | 판매가격, 건당 변동비 |
| 혜택 재설계 | 적용 조건과 비용 범위 조정 | 판매가격(실수령), 적용 비율 |
| 판매 노출 개선 | 메뉴 설명과 배치 변경 | 도입비용, 판매 구성 |
| 주문·운영 편의 개선 | 주문 과정과 수용 방식 개선 | 도입비용, 추가 조리시간 |

각 후보마다 다음을 함께 표시한다. **건당 공헌이익만으로 순위를 매기지 않는다.**

- 대상 수요 규모 (단계 2 진단의 집단 비중과 연결)
- 건당 공헌이익
- 도입 비용
- 추가 조리시간
- 기존 메뉴 판매 감소 가능성 (잠식률)

## 매장 전체 공헌이익 비교

메뉴 1개만 보면 잘못된 결론이 난다. 대표 메뉴 3개를 함께 두고 매장 전체를 계산한다.

```
매장 일평균 공헌이익 = Σ(메뉴별 건당 공헌이익 × 메뉴별 일평균 판매량)
```

- 한 메뉴의 가격을 내리면 다른 메뉴 판매량이 줄어드는 **잠식률**을 입력받는다 (기본 0%, 사용자 조정).
- 주요 재료 가격 상승은 해당 재료를 쓰는 메뉴의 변동비에만 적용한다 (단계 5 연계).

## 자료 부족 시 동작

| 상황 | 처리 |
| --- | --- |
| 판매량을 모름 | 기존 판매량을 **100 지수**로 두고 필요 **증가율**만 제시 |
| 원가를 정확히 모름 | **낮음 / 기준 / 높음** 3개 값으로 입력받고 3개 결과를 병기 |
| 매장 자료가 전혀 없음 | 공개 메뉴 가격·레시피 기반 **예시 매장**으로 시연. "가상 사례" 배지 고정 표시 |

모든 입력 필드에 **관측값 / 추정값 / 가정값** 태그를 붙이고, 결과 화면에 어떤 태그가 섞였는지 요약한다.

## 예시 매장 구성 (업종별 2종)

업종마다 객단가 구조가 달라 대안의 효과도 다르게 나온다. 예시 매장을 업종별로 따로 만든다.

### 예시 매장 A — 일반한식

- 대표 메뉴 3개: 백반류 / 찌개류 / 면류
- 참조 객단가: 전국 일반한식 건당 36,321원 (B기간). 단 이 값은 **결제 1건 기준**이며 1인 식사 가격이 아니다. 동반 인원이 섞여 있다.
- 메뉴 가격은 1인 기준으로 설정하고, 결제 건당 평균 인원을 가정값으로 명시한다.

### 예시 매장 B — 서양음식

- 대표 메뉴 3개: 파스타류 / 피자류 / 단품+음료 세트
- 참조 객단가: 전국 서양음식 건당 10,630원 (B기간)
- 한식보다 객단가가 3배 이상 낮으므로 **도입비용의 상대적 부담이 훨씬 크다.** 예컨대 30만 원짜리 메뉴판 개편은 한식 매장보다 서양음식 매장에서 회수에 필요한 추가 판매량이 크게 늘어난다. 이 차이가 화면에서 드러나야 한다.

### 공통 규칙

- 가격은 공개 정보 기준, 원가는 레시피와 식재료 공개 가격 기반 추정
- 두 예시 매장의 결과를 나란히 놓지 않는다. 사용자는 자기 업종 하나만 본다
- **실제 매장의 수익성이나 서비스 도입 효과를 검증한 것으로 표현하지 않는다**

### 업종별 객단가 차이가 만드는 진단 차이

| | 일반한식 | 서양음식 |
| --- | --- | --- |
| 전국 건당금액 (B) | 36,321원 | 10,630원 |
| 전국 건당금액 변화 | −1.78% | −6.39% |
| 같은 1,000원 할인의 비중 | 2.8% | 9.4% |
| 같은 30만 원 도입비 회수 난이도 | 낮음 | 높음 |

서양음식은 객단가가 낮아 **할인 한 번의 공헌이익 타격이 3배 이상 크다.** 동일한 "10% 할인" 대안이라도 업종에 따라 필요 판매량 증가율이 크게 달라지므로, 대안 카탈로그에 업종별 기본값을 둔다.

## 검증 기준

- [ ] 검산 예시 3행이 100 / 120 / 106으로 재현된다
- [ ] 공헌이익 0 이하일 때 숫자 대신 불가 메시지가 나온다
- [ ] 공헌이익 0.01원일 때 오버플로 없이 처리된다
- [ ] 올림 경계값 테스트 (`600000 ÷ 6000 = 100.0` → 100, `÷5999` → 101)
- [ ] 도입비용 0원과 양수 모두에서 식이 성립한다
- [ ] 판매량 미입력 시 지수 100 기준 증가율이 나온다
- [ ] 원가 범위 입력 시 3개 결과가 모두 표시된다
- [ ] 예시 매장 A(한식)와 B(서양음식) 모두에서 동일 대안이 계산되고, 서양음식 쪽 필요 판매량 증가율이 더 크게 나온다
- [ ] 도입비용이 있는 대안에서 업종별 회수 난이도 차이가 수치로 드러난다
- [ ] 건당 결제금액이 1인 식사 가격이 아니라는 주석이 있다
- [ ] 화면에 "필요 판매량은 달성 조건이며 판매 예측이 아니다" 문구가 있다
- [ ] 예시 매장에 "가상 사례" 표시가 있다

## 리스크

| 리스크 | 대응 |
